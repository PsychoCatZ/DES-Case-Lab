# DES Case Lab — план Day 2

## Цель

Перевести DES Case Lab из локального MVP с `LocalStorage` в клиент-серверное приложение с backend/API, не переписывая существующий интерфейс и доменную логику.

Архитектурная идея Day 1 должна сохраниться:

```text
UI
 ↓
useCases
 ↓
CaseRepository
 ↓
ApiCaseRepository
 ↓
HTTP API
```

## 1. Подключить backend/API

Реализовать backend с HTTP API для основных операций с кейсами:

- получение списка кейсов;
- создание кейса;
- редактирование кейса;
- удаление кейса.

Конкретный backend-фреймворк, база данных и хостинг будут выбраны отдельно перед реализацией.

## 2. Реализовать `ApiCaseRepository`

Добавить реализацию `ApiCaseRepository`, совместимую с уже существующим контрактом `CaseRepository`.

Цель — заменить:

```text
LocalCaseRepository → LocalStorage
```

на:

```text
ApiCaseRepository → HTTP API
```

без переработки форм, таблицы, мобильных карточек, фильтров, KPI и статистики.

## 3. Добавить состояния сетевой работы

Интерфейс должен корректно обрабатывать:

- загрузку данных;
- сохранение изменений;
- удаление кейса;
- временную недоступность backend;
- сетевые ошибки;
- повторный запрос после ошибки.

Во время операций, где повторное действие может привести к дублям или конфликтам, соответствующие кнопки должны временно блокироваться.

## 4. Настроить конфигурацию

Адрес backend/API и другие параметры окружения не должны быть жёстко прописаны в компонентах.

Если потребуются переменные окружения:

- использовать `.env`;
- не хранить секреты в Git;
- добавить безопасный `.env.example` только с именами переменных и демонстрационными/пустыми значениями.

Секретные ключи не должны попадать во frontend-код.

## 5. Определить стратегию перехода с LocalStorage

Day 1 хранит данные отдельно в каждом браузере.

Перед переходом на backend необходимо определить, что делать с уже существующими локальными кейсами:

- оставить их только как данные Day 1;
- предложить перенос в backend;
- либо использовать LocalStorage только как fallback/development-хранилище.

Выбранное поведение должно быть явным и не приводить к неожиданной потере данных.

## 6. Сохранить поведение Day 1

После подключения API должны продолжить работать:

- создание, редактирование и удаление кейсов;
- подтверждение удаления;
- фильтры по модели, модулю и статусу;
- KPI по общему числу кейсов и статусам;
- диаграмма распределения кейсов по моделям;
- сортировка по `createdAt`;
- desktop-таблица;
- mobile-карточки;
- пустые состояния;
- адаптивный интерфейс.

## 7. Обновить тесты

Добавить или скорректировать тесты для:

- `ApiCaseRepository`;
- успешных HTTP-операций;
- сетевых ошибок;
- loading/error-состояний;
- сохранения существующей логики фильтров и статистики.

Перед завершением Day 2 повторно выполнить:

- Vitest;
- проверку TypeScript;
- ESLint;
- production build.

## 8. Развёртывание

Подготовить production-версию проекта и выполнить развёртывание frontend и backend.

После развёртывания проверить полный пользовательский сценарий:

1. открыть приложение;
2. загрузить список кейсов;
3. создать кейс;
4. отредактировать его;
5. проверить пересчёт KPI и диаграммы;
6. применить фильтры;
7. удалить кейс;
8. обновить страницу и убедиться, что данные сохранились на backend.

## Критерии готовности Day 2

Day 2 считается завершённым, если:

- приложение работает через backend/API;
- `ApiCaseRepository` подключён через существующий `CaseRepository`;
- UI не потребовал архитектурного переписывания;
- CRUD работает после перезагрузки страницы и не зависит от конкретного браузера;
- сетевые состояния и ошибки обрабатываются в интерфейсе;
- секреты отсутствуют в репозитории и frontend-коде;
- автоматические проверки проходят;
- production build успешен;
- развёрнутая версия проходит основной ручной сценарий.

## Ожидаемый результат

DES Case Lab превращается из локального Day 1 MVP в развёртываемое клиент-серверное приложение, при этом архитектурные решения первого дня сохраняются и используются как основа дальнейшего развития.
