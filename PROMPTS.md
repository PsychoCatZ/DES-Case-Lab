# DES Case Lab — ключевые промпты Day 1

Этот файл содержит ключевые запросы, уточнения и решения, использованные при разработке Day 1 MVP проекта DES Case Lab.

Промпты приведены в сокращённом виде: повторяющиеся обсуждения и промежуточные реплики исключены, но сохранены основные требования, архитектурные решения и корректировки, которые повлияли на итоговую реализацию.

Помимо ключевых промптов, файл содержит краткие результаты ручных проверок и последующих корректировок, если они напрямую повлияли на разработку.

## 1. Постановка задачи

Нужно разработать демонстрационный веб-проект DES Case Lab — интерактивный дашборд для фиксации и сравнения результатов экспертных AI-моделей.

На Day 1 нужен локально работающий frontend без backend и внешних API.

Основные сущности:

- кейсы;
- модули DES: `Genre`, `Scene`, `Photo`, `Text`;
- модели: `Sol`, `DeepSeek`, `Astra`;
- статусы: `Принят`, `Ошибка`, `На проверке`.

Для каждого кейса необходимо хранить:

- название или краткое описание;
- модуль;
- модель;
- ответ модели;
- статус.

Основные возможности:

- добавление кейса;
- редактирование кейса;
- удаление кейса;
- журнал всех кейсов;
- фильтрация по модели, модулю и статусу;
- KPI по количеству кейсов и статусам;
- статистика по моделям;
- сохранение данных после перезагрузки страницы.

Интерфейс нужен в тёмном технологичном стиле DES. Он должен нормально работать на desktop и мобильных экранах.

На первом этапе данные можно хранить в LocalStorage.

Перед реализацией сначала предложи архитектуру проекта. Код пока не пиши.

## 2. Требования к архитектуре

Архитектура должна оставаться достаточно простой, чтобы её можно было понять и объяснить, но при этом не создавать тупик перед Day 2.

На Day 2 LocalStorage планируется заменить на backend/API. Желательно сделать это без полной переработки интерфейса.

Предложи:

- стек;
- структуру каталогов;
- основные компоненты;
- модель данных кейса;
- управление состоянием;
- способ работы с LocalStorage;
- подход к будущему API;
- способ построения простой статистики.

Не добавляй библиотеки без необходимости.

Отдельно объясни назначение предложенных технологий и архитектурных решений.

## 3. Уточнение поведения MVP

После обсуждения архитектуры зафиксированы следующие правила:

- KPI и статистика по моделям считаются по всем сохранённым кейсам и не зависят от активных фильтров;
- фильтры по модели, модулю и статусу комбинируются по принципу AND;
- должна быть кнопка сброса фильтров;
- фильтры после перезагрузки страницы не сохраняются;
- кейсы сортируются по `createdAt`, новые сверху;
- редактирование кейса не должно перемещать его вверх списка;
- удаление должно требовать подтверждения;
- название и ответ модели обязательны;
- текстовые значения перед сохранением необходимо очищать от лишних пробелов;
- изменения сохраняются только после явного действия пользователя.

Для длинных ответов в журнале показывай сокращённую версию, но при редактировании должен быть доступен полный текст.

## 4. Адаптивный интерфейс

На desktop журнал может отображаться таблицей.

На мобильном экране не нужно пытаться сжать эту таблицу до нечитаемого состояния. Замени её представлением в виде карточек с теми же данными и действиями.

Форма добавления и редактирования должна быть общей, чтобы не дублировать бизнес-логику.

Для модальных окон используй минимальное решение без тяжёлой UI-библиотеки. Можно использовать нативный `<dialog>` с оформлением приложения.

Нужны два разных пустых состояния:

1. в журнале вообще нет кейсов;
2. кейсы существуют, но активные фильтры ничего не нашли.

## 5. Статистика без лишней зависимости

Для текущего MVP отдельная библиотека графиков не нужна.

Покажи распределение кейсов по моделям `Sol`, `DeepSeek` и `Astra` простыми горизонтальными CSS-барами.

Для каждой модели должны быть понятны количество кейсов и её доля.

Предусмотри корректное состояние, если кейсов пока нет.

## 6. Подготовка LocalStorage к будущему API

Не связывай компоненты интерфейса напрямую с LocalStorage.

Используй отдельный контракт `CaseRepository`.

Для Day 1 реализуй:

```text
UI
 ↓
useCases
 ↓
CaseRepository
 ↓
LocalCaseRepository
 ↓
LocalStorage
```

Контракт репозитория сразу сделай асинхронным.

На Day 2 должна появиться возможность реализовать:

```text
UI
 ↓
useCases
 ↓
ApiCaseRepository
 ↓
HTTP API
```

без переписывания форм, таблицы, фильтров, KPI и статистики.

## 7. Первый запуск и восстановление данных

При первом запуске приложение должно создавать несколько демонстрационных кейсов.

Если пользователь удалил все кейсы и в LocalStorage сохранён пустой массив, приложение не должно считать это первым запуском и восстанавливать демонстрационные данные заново.

Отдельно обработай повреждённые данные LocalStorage.

Перед автоматическим восстановлением попробуй сохранить исходную повреждённую строку в резервный ключ вида:

`des-case-lab:cases:recovery:<timestamp>`

Только после успешного резервного сохранения можно перезаписать основной ключ демонстрационными данными.

Если резервное сохранение не удалось, не уничтожай исходные данные. Приложение может временно показать демонстрационные данные в памяти и сообщить пользователю о проблеме.

## 8. Реализация Day 1

Архитектура и поведение согласованы.

Можно приступать к реализации Day 1 MVP.

Используй согласованный стек:

- React 19;
- TypeScript;
- Vite;
- обычный CSS с переменными;
- Vitest;
- React Testing Library;
- ESLint.

Не добавляй backend, API, авторизацию, облачное хранилище или другие функции Day 2.

После реализации:

- запусти тесты;
- проверь TypeScript;
- проверь ESLint;
- собери production build;
- сообщи результаты проверок.

## 9. Ручная проверка MVP

После реализации приложение было дополнительно проверено вручную.

Подтверждено:

- новый кейс создаётся;
- существующий кейс редактируется;
- кейс удаляется после подтверждения;
- KPI-карточки по общему числу кейсов и статусам пересчитываются;
- диаграмма распределения кейсов по моделям пересчитывается;
- фильтры работают совместно;
- изменения сохраняются после обновления и повторного открытия страницы в том же браузере;
- мобильное представление заменяет таблицу карточками;
- интерфейс остаётся работоспособным при узкой и горизонтальной мобильной ориентации.

Дополнительно проверено поведение LocalStorage:

- изменения сохраняются в рамках того же браузера и профиля;
- в другом браузере открывается отдельное локальное хранилище;
- это соответствует архитектуре Day 1 и не считается ошибкой.

По итогам ручной проверки критических проблем в основных сценариях MVP не обнаружено.

## 10. Исправление демонстрационных кейсов

После ручной проверки обнаружено, что демонстрационные данные слишком свободно интерпретируют назначение реальных модулей DES.

Архитектуру приложения менять не нужно. Исправь только демонстрационные кейсы и ответы так, чтобы они правдоподобно показывали назначение модулей.

### Genre

`Genre` выполняет разметку изображения по двум независимым категориям.

Стилистика — один или несколько тегов из закрытого списка:

- `Черно-белая`
- `Кинематографичная`
- `Минималистичная`
- `Неоновая`
- `Пастельная`
- `Яркая`
- `Винтажная`
- `Нет стилистики`

Жанр — ровно один тег из закрытого списка:

- `Нет жанра`
- `Реклама / рекламный креатив`
- `Архитектура`
- `Пейзаж`
- `Пакшот (товар на фоне)`
- `Портрет`
- `Постер / афиша`
- `Натюрморт`
- `Стрит-фотография`
- `Дикая природа (жанр)`

Демонстрационный ответ должен показывать обе категории. Если выбрано несколько стилистик, это допустимо.

Не превращай `Genre` в эксперта по жанрам кино.

### Scene

`Scene` работает с последовательностью кадров одного видеосегмента и составляет цельное описание происходящей сцены.

Демонстрационный кейс должен показывать изменение действия во времени, а не классификацию отдельного изображения.

### Photo

`Photo` выполняет разметку изображения по двум категориям.

Синтетические элементы — теги из закрытого списка:

- `Нет синтетических элементов`
- `Аннотации и разметка`
- `Брендинг и водяные знаки`
- `Коды и идентификаторы`
- `Датавиз и графика`
- `Символы и знаки`
- `Системные оверлеи`
- `Текстовые элементы`
- `UI элементы`

Визуальные атрибуты — теги из закрытого списка:

- `Нет визуальных атрибутов`
- `Узор / рисунок`
- `Белый фон`

Демонстрационный кейс должен отражать именно такую разметку либо правдоподобную ошибку модели при её выполнении.

### Text

`Text` работает с текстовым содержанием и его нормализацией/редактированием в соответствии с правилами задачи.

Демонстрационный кейс должен содержать исходный текст и правдоподобный нормализованный результат.

Не добавляй внутренние правила, которых нет в переданных требованиях.

## 11. Подготовка первого Git-коммита

Перед первым коммитом:

- проверь состав проекта;
- не включай `node_modules/`, `dist/`, `coverage/`, `.vite/`;
- не включай `.env` и другие файлы с секретами;
- не включай служебные каталоги IDE и Codex;
- проверь staged-файлы на случайные токены, API-ключи, credentials и приватные ключи;
- повторно запусти тесты, TypeScript, ESLint и production build.

Первый коммит должен содержать только исходники приложения, тесты и необходимые конфигурационные файлы.

Сообщение коммита:

`feat: add Day 1 DES Case Lab MVP`

Не выполняй force-push и не перезаписывай неожиданно существующую историю удалённого репозитория.
